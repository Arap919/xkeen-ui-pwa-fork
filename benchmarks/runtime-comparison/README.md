# Сравнение Go и Rust на MIPSel

Экспериментальный прототип. Рабочую панель не заменяет. Сервисы слушают только
`127.0.0.1:18081`, запускаются по очереди с одинаковым `fixture.json`.

Сценарии: `/health` — минимальный JSON; `/json` — сериализация 128 узлов;
`/system` — запрос к настоящему RCI с повторным использованием HTTP-соединений.
Токен RCI читается из существующего `/opt/etc/xkeen/xkeen.json`, без вывода в лог.
`BENCH_RCI_URL` позволяет проверить обработчики с локальным тестовым RCI.
Обработчик `/system` возвращает полный JSON RCI; это сравнение прототипов,
а не точная копия действующего API панели. TLS, WebSocket, работа с логами,
редактором и Mihomo здесь пока не измеряются.

## Сборка

Из этой папки:

```sh
mkdir -p bin
(cd go && CGO_ENABLED=0 GOOS=linux GOARCH=mipsle GOMIPS=softfloat go build -trimpath -ldflags='-s -w' -o ../bin/server-go .)
(cd load && CGO_ENABLED=0 GOOS=linux GOARCH=mipsle GOMIPS=softfloat go build -trimpath -ldflags='-s -w' -o ../bin/load .)
(cd rust && RUSTFLAGS='-C target-feature=+crt-static -L /usr/local/mipsel-linux-muslsf/lib -L /usr/local/lib/gcc/mipsel-linux-muslsf/9.2.0' cross +nightly build --release --target mipsel-unknown-linux-musl)
cp rust/target/mipsel-unknown-linux-musl/release/runtime-bench-rust bin/server-rust
```

## Методика

Сначала проверить ядро, архитектуру, свободную память и `getconf CLK_TCK` на
роутере. Загружать в отдельный временный каталог. Не менять init-скрипты,
настройки панели, proxy-ядра и маршрутизацию. Не отключать проверку SSH-ключа.
Оба сервера должны работать в обычном режиме рантайма, без искусственного
ограничения одного из них одним потоком. Записать версии toolchain и CPU.

Запускать каждый сервер отдельно, сохраняя PID, и измерять `load` на самом
роутере. До и после каждого сценария проверять отсутствие ошибок. Пример:

```sh
./server-go -listen 127.0.0.1:18081 -fixture fixture.json >server.log 2>&1 &
pid=$!
./load -url http://127.0.0.1:18081/json -pid "$pid" -hz 100 -concurrency 1 -duration 8s
kill "$pid"
wait "$pid"
```

`-hz 100` выше — только пример: подставить фактический результат
`getconf CLK_TCK`; если получить его нельзя, не передавать `-hz`.
Rust принимает `--listen` и `--fixture` с теми же значениями.

Провести минимум пять парных раундов с чередованием Go→Rust и Rust→Go.
Для `/health` и `/json` измерять максимальную пропускную способность при
concurrency 1 и 4. Для настоящего `/system` использовать `-rate 1`
и concurrency 1, чтобы не забивать RCI запросами; при таком режиме RPS
задан нагрузкой, сравнивать задержки и ресурсы. Между серверами делать
паузу; сохранять исходные JSON результатов с отметкой времени.

Сравнивать медианы по раундам, p95, ошибки, RSS и CPU на одинаковой работе.
CPU при максимальной нагрузке дополнительно нормировать на число запросов.
RSS до/после и VmHWM — снимки процесса; VmHWM накоплен с момента запуска.
Генератор тоже расходует CPU роутера, поэтому результаты показывают работу
при общей нагрузке двух процессов, а не абсолютную мощность HTTP-сервера.
Не использовать эти цифры как скорость всей панели или пропускную способность VPN.

Разница менее 10% — предварительно «сопоставимо», только если разброс
повторных измерений достаточно мал. При большом разбросе вывод неопределён.
Если Go сопоставим или быстрее по задержкам, но заметно хуже по памяти,
это отдельный компромисс для обсуждения перед переписью. После сравнения
удалить только созданные процессы и временный каталог эксперимента.

## Запуск подготовленного сравнения

После сборки и настройки SSH-доступа по проверенному ключу:

```sh
python3 run_router.py --rounds 5 --label go-use-number
```

Только повтор JSON-сценариев:

```sh
python3 run_router.py --rounds 5 --cases json --label go-use-number
```

Скрипт сохраняет локальные результаты в `results/`, запускает серверы по
очереди во временном каталоге роутера и удаляет только свои процессы и файлы.
Текущий Go-прототип использует `UseNumber()` для сохранения JSON-чисел.

Результаты выполненного сравнения: [RESULTS.md](RESULTS.md).
