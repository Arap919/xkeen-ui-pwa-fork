# XKeen UI PWA: локальный HTTPS и установка

Это руководство описывает прямой HTTPS в XKeen UI backend на порту `1000`:

- backend загружает server certificate и key из `/opt/etc/nginx/ssl/`;
- отдельный Nginx reverse proxy для панели не требуется;
- локальный центр сертификации (CA) создаётся на Mac; его закрытый ключ остаётся на компьютере;
- сертификат CA устанавливается как доверенный на устройствах, с которых нужно открывать панель и устанавливать PWA.

Пример рассчитан на Keenetic Giant (KN-2610 EAEU) с Entware, доступным по SSH на порту `222`, и IP роутера `192.168.1.1`. Если адрес или порт SSH у вас другие, замените их во всех командах. Не пробрасывайте порт HTTPS-панели из интернета.

## 1. Подготовка роутера

### Проверить Entware и подготовить каталог сертификатов

Подключитесь к Entware:

```sh
ssh -p 222 root@192.168.1.1
```

Создайте каталог, в который будут помещены TLS-файлы:

```sh
mkdir -p /opt/etc/nginx/ssl
```

Entware Nginx не нужен для HTTPS самого XKeen UI. Не меняйте конфигурацию штатного Nginx Keenetic.

## 2. Выпуск локального CA и сертификата панели на Mac

Откройте Terminal на Mac:

```sh
mkdir -p ~/xkeen-ui-local-tls
cd ~/xkeen-ui-local-tls
```

Создайте конфигурацию локального центра сертификации:

```sh
cat > ca.cnf <<'EOF'
[req]
prompt = no
distinguished_name = dn
x509_extensions = v3_ca

[dn]
CN = XKeen UI Home CA

[v3_ca]
basicConstraints = critical, CA:TRUE
keyUsage = critical, keyCertSign, cRLSign
subjectKeyIdentifier = hash
EOF
```

Создайте CA и защитите его закрытый ключ:

```sh
openssl req -x509 -newkey rsa:3072 -nodes \
  -keyout ca.key -out ca.crt -days 3650 \
  -sha256 -config ca.cnf -extensions v3_ca
chmod 600 ca.key
```

`ca.key` — главный секрет CA. Он нужен для выпуска сертификатов. Не загружайте его на роутер, телефон или в облако и не отправляйте другим людям. Для доверия устройств используется только открытый сертификат `ca.crt`.

Создайте конфигурацию серверного сертификата. SAN (Subject Alternative Name) должен содержать IP-адрес, по которому устройства открывают панель:

```sh
cat > server.cnf <<'EOF'
[req]
prompt = no
distinguished_name = dn
req_extensions = req_ext

[dn]
CN = 192.168.1.1

[req_ext]
subjectAltName = @alt_names

[server_ext]
basicConstraints = critical, CA:FALSE
keyUsage = critical, digitalSignature, keyEncipherment
extendedKeyUsage = serverAuth
subjectAltName = @alt_names

[alt_names]
IP.1 = 192.168.1.1
EOF
```

Если IP роутера отличается, измените и `CN`, и `IP.1` на его адрес до выпуска сертификата.

Выпустите сертификат панели и проверьте SAN:

```sh
openssl req -new -newkey rsa:2048 -nodes \
  -keyout server.key -out server.csr -config server.cnf

openssl x509 -req -in server.csr \
  -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out server.crt -days 397 -sha256 \
  -extfile server.cnf -extensions server_ext

chmod 600 server.key
openssl x509 -in server.crt -noout -subject -ext subjectAltName
```

В выводе SAN ожидается `IP Address:192.168.1.1`. Если IP не указан или неверен, браузер не сможет проверить, что сертификат выдан для открываемого адреса.

## 3. Установить сертификат панели на роутер

С Mac скопируйте на роутер **только** серверный сертификат и его закрытый ключ. Backend по умолчанию проверяет эти пути:

```sh
ssh -p 222 root@192.168.1.1 'mkdir -p /opt/etc/nginx/ssl'
scp -O -P 222 server.crt server.key \
  root@192.168.1.1:/opt/etc/nginx/ssl/
```

Флаг `-O` включает старый SCP-протокол: в используемой конфигурации Entware отсутствует SFTP-сервер. Флаг `-P 222` задаёт SSH-порт Entware.

На роутере ограничьте доступ к ключу и оставьте сертификат доступным для чтения:

```sh
chmod 600 /opt/etc/nginx/ssl/server.key
chmod 644 /opt/etc/nginx/ssl/server.crt
```

Если сертификаты уже установлены, переустановите/обновите пакет XKeen UI: установщик сформирует init-скрипт с TLS-флагами автоматически. Новый backend также автоматически включает TLS при наличии обоих файлов в этих стандартных путях, поэтому прежний init-скрипт с `ARGS="-p 1000"` тоже переключится на HTTPS после обновления и перезапуска. Если панель уже установлена, можно явно пересоздать init-скрипт и перезапустить сервис:

```sh
/opt/sbin/xkeen-ui create-init
/opt/etc/init.d/S99xkeen-ui restart
```

Проверьте лог и порт:

```sh
tail -n 50 /opt/var/log/xkeen-ui.log
netstat -lntp 2>/dev/null | grep ':1000'
```

При активном TLS лог сообщает `Listening on https://0.0.0.0:1000`. Открывайте панель напрямую:

```text
https://192.168.1.1:1000
```

Порт `1000` остаётся прежним, но при включённом TLS принимает HTTPS, в том числе WebSocket. Если ранее был настроен отдельный Entware Nginx reverse proxy на `9443`, остановите его: его upstream `http://127.0.0.1:1000` больше не подходит, когда backend работает с TLS. Если этот экземпляр был запущен с указанным ниже конфигом, остановите именно его так:

```sh
/opt/sbin/nginx -s stop -c /opt/etc/nginx/xkeen-ui-https.conf
```

Не меняйте скрипт штатного Nginx Keenetic. При переходе с `https://192.168.1.1:9443` на `https://192.168.1.1:1000` браузер считает это другим origin; установленную PWA нужно установить заново. Для намеренного запуска по HTTP при установленных сертификатах добавьте `--no-tls` в `ARGS` init-скрипта.

## 5. Установить и доверить CA на устройствах

Устанавливайте на клиентские устройства **только `ca.crt`**. Сертификат панели `server.crt` и ключи `server.key`/`ca.key` для доверия клиенту не нужны.

### macOS

1. Откройте Finder, нажмите `Command+Shift+G` и введите `~/xkeen-ui-local-tls/ca.crt`.
2. Откройте `ca.crt` в «Связке ключей».
3. Добавьте сертификат в связку «Вход» или «Система». В «Связке ключей» откройте сертификат `XKeen UI Home CA`, раскройте раздел «Доверие» и установите «При использовании этого сертификата» → «Всегда доверять». Подтвердите изменение паролем Mac, если потребуется.
4. Откройте `https://192.168.1.1:1000` в браузере.

Если сертификат добавлен только в связку «Вход», доверие может распространяться только на текущего пользователя. Для всех пользователей Mac добавляйте его в связку «Система».

### Windows

Передайте `ca.crt` на Windows любым доверенным способом. Не передавайте `ca.key`.

1. Нажмите `Win+R`, введите `certmgr.msc` и нажмите Enter.
2. В дереве выберите **Сертификаты — текущий пользователь → Доверенные корневые центры сертификации → Сертификаты**.
3. Выберите **Действие → Все задачи → Импорт**, укажите `ca.crt` и поместите сертификат именно в хранилище **«Доверенные корневые центры сертификации»**.
4. Если сертификат нужен всем пользователям компьютера, импортируйте его через `certlm.msc` в аналогичное хранилище локального компьютера; для этого потребуются права администратора.
5. Перезапустите браузер и откройте `https://192.168.1.1:1000`.

На Windows также можно выпустить сертификаты командами OpenSSL из WSL, Git Bash или другой доверенной установки OpenSSL. Конфиги и команды выпуска приведены в разделе для Mac и выполняются в оболочке Bash; закрытый ключ CA храните в безопасном месте.

### iPhone и iPad

Передайте на устройство только `ca.crt`, например через AirDrop, и сохраните или откройте полученный файл.

1. Если iOS сообщит о загруженном профиле, откройте **Настройки → Основные → VPN и управление устройством**, выберите профиль и нажмите «Установить».
2. Затем откройте **Настройки → Основные → Об этом устройстве → Доверие сертификатам**.
3. Включите полное доверие для `XKeen UI Home CA` и подтвердите действие.
4. Подключите устройство к домашнему Wi-Fi и откройте в Safari `https://192.168.1.1:1000`.
5. В Safari нажмите **Поделиться → На экран «Домой»**, чтобы добавить панель как приложение.

Установка профиля и его полное доверие — отдельные шаги. Одной установки профиля может быть недостаточно для доверия пользовательскому корневому CA.

## 6. Установка PWA и работа офлайн

После успешного открытия панели по HTTPS:

- **Chrome/Edge на компьютере и Android:** используйте предложение установки в адресной строке или меню браузера → «Установить приложение» / «Добавить на главный экран».
- **iPhone/iPad:** в Safari используйте **Поделиться → На экран «Домой»**.

PWA требует безопасного контекста: HTTPS с доверенным сертификатом или `localhost`. Обычный `http://192.168.1.1:1000` не даёт браузеру надёжно регистрировать service worker и устанавливать приложение.

Service worker кэширует оболочку и статические ресурсы приложения, но не кэширует API, WebSocket и данные роутера. Поэтому без сети может открыться оболочка, но управление роутером и загрузка его данных требуют соединения с ним.

## 7. Выявленные проблемы и решения

### `RustEmbed` не находит `frontend/dist`

Сообщение вида:

```text
#[derive(RustEmbed)] folder '../frontend/dist' does not exist
```

Означает, что production-фронтенд ещё не собран или недоступен из каталога исходников backend. Сначала выполните сборку во `frontend`:

```sh
cd frontend
npx --yes bun@latest run build
```

Для кросс-сборки через Docker `cross` используйте временную копию backend и положите `frontend/dist` внутрь неё как `backend/dist`. В копии замените путь `#[folder = "../frontend/dist"]` на `#[folder = "./dist"]`, чтобы ресурс был доступен внутри контейнера. Исходный backend при этом менять не требуется.

Ошибка `StaticFiles::get` вместе с этой ошибкой — следствие того, что derive-макрос `RustEmbed` не смог прочитать каталог и сгенерировать методы структуры.

### `cross` сообщает, что `rust-std` недоступен для MIPS

Для `mipsel-unknown-linux-musl` нужна nightly-сборка Rust с `rust-src` и сборка стандартной библиотеки:

```sh
rustup toolchain install nightly --profile minimal -c rust-src
```

Используйте `cross +nightly` и добавьте `build-std` в секцию соответствующей цели в `Cross.toml`, сохранив уже заданные для цели параметры образа и `pre-build`:

```toml
build-std = ["std", "panic_abort", "proc_macro"]
```

Например:

```toml
[target.mipsel-unknown-linux-musl]
image = "ghcr.io/cross-rs/mipsel-unknown-linux-musl:edge"
build-std = ["std", "panic_abort", "proc_macro"]
```

При работе во временной копии настройте `Cross.toml` именно в копии.

### SCP сообщает `Permission denied`

Убедитесь, что используется SSH-порт Entware `222`, а не стандартный порт `22`:

```sh
scp -O -P 222 файл root@192.168.1.1:/opt/tmp/
```

Для `ssh` параметр порта записывается строчной буквой: `ssh -p 222 root@192.168.1.1`.

### SCP сообщает `/opt/libexec/sftp-server: not found`

В Entware может отсутствовать SFTP-сервер. Используйте старый SCP-протокол с заглавным флагом `-O`:

```sh
scp -O -P 222 файл root@192.168.1.1:/opt/tmp/
```

При переносе команды на следующую строку символ `\` должен быть последним символом строки — без пробелов после него.

### Ошибки Nginx при настройке прежнего HTTPS reverse proxy

Для актуальной схемы Nginx reverse proxy не нужен: TLS завершается непосредственно в backend на порту `1000`. Ранее использовавшаяся прокси-конфигурация могла конфликтовать со встроенным Nginx Keenetic на портах `80`/`8443` или выдавать `getgrnam("nogroup") failed`; не запускайте для панели стандартный Entware-конфиг на `80`. Если сохраняете старый прокси для других задач, ему нужны отдельный свободный порт, отдельный конфиг и доступный пользователь Nginx (в проверенной конфигурации — `user nobody;`). Для PWA используйте прямой адрес backend `https://192.168.1.1:1000`.

### Браузер предупреждает о сертификате или PWA не устанавливается

Проверьте все условия:

1. Открывается HTTPS-адрес `https://192.168.1.1:1000`.
2. `server.crt` содержит SAN `IP Address:192.168.1.1` (или актуальный IP роутера).
3. На устройстве установлен и помечен как доверенный именно `ca.crt`.
4. Устройство подключено к домашней сети и может достичь `192.168.1.1`.
5. После установки корневого сертификата браузер был перезапущен, если это необходимо.

Самоподписанный `server.crt`, не выданный доверенным на клиентском устройстве CA, вызовет предупреждение. Сертификат для одного IP также не подойдёт, если панель открыть по другому IP или имени хоста.

### Backend не запускается с TLS

Проверьте наличие обоих файлов, права на закрытый ключ и корректность PEM:

```sh
ls -l /opt/etc/nginx/ssl/server.crt /opt/etc/nginx/ssl/server.key
openssl x509 -in /opt/etc/nginx/ssl/server.crt -noout -subject -ext subjectAltName
```

В `/opt/var/log/xkeen-ui.log` будет указана причина ошибки загрузки сертификата/ключа. TLS-файлы должны быть PEM и содержать сертификат, соответствующий закрытому ключу. Проверьте, что init-скрипт включает **оба** параметра `--tls-cert` и `--tls-key`; если сертификаты были добавлены после установки, выполните `xkeen-ui create-init` и перезапустите сервис.

### Панель всё ещё работает по HTTP

Установщик включает TLS только когда одновременно существуют оба файла `/opt/etc/nginx/ssl/server.crt` и `/opt/etc/nginx/ssl/server.key`. Новый backend также проверяет эти пути сам при запуске без TLS-параметров. Проверьте `ARGS` в `/opt/etc/init.d/S99xkeen-ui`, убедитесь, что приложение обновлено до версии с TLS, затем выполните `/opt/etc/init.d/S99xkeen-ui restart`. После добавления сертификатов пересоздайте скрипт командой `/opt/sbin/xkeen-ui create-init`.

### `https://...:1000` не открывается после переключения с Nginx reverse proxy

Старый reverse proxy передавал на порт `1000` обычный HTTP. При включении прямого TLS такой прокси перестаёт работать. Откройте backend напрямую по `https://192.168.1.1:1000` и отключите старый отдельный Nginx proxy, либо верните HTTP-режим, убрав TLS-параметры из `ARGS` init-скрипта.
