# Встроенный watchdog и снижение нагрузки панели

Статус: проект с уточнением пользователя от 14 ноября 2026 года.
Встроенный watchdog включён по умолчанию и управляется из отдельной вкладки
настроек панели; откат к Python-версии не предусматривается.

## Цель и выбранный подход

Перенести автоматическую работу router-watchdog в существующий Rust-бэкенд,
приостанавливать поток соединений Mihomo и опрос статуса/метрик в скрытой
вкладке, объединить повторяющиеся запросы между клиентами через общий кеш.

Пользователь выбрал встроенную задачу в текущем бэкенде. Отдельный Rust-демон
сохранил бы независимость watchdog, но оставил бы дополнительный процесс.
Запуск Python из панели сохранил бы дорогую инициализацию Python при каждой
проверке. Реализуется встроенный Rust-вариант; Go и Angular сюда не входят.

## Сохраняемое поведение watchdog

Источник истины — текущая реализация и тесты в `/Users/olegfirskov/router-watchdog`.
На момент диагностики SHA-256 локального runtime совпал с установленным.
Текущий `backend/src/watchdog.rs` управляет обновлением и Push, а не failover:
новый движок получает отдельный модуль `backend/src/watchdog_engine/`.

- Сохранить `/opt/etc/router-watchdog.json`, текущую схему и значения настроек,
  переменные `ROUTER_WATCHDOG_CONFIG`, `ROUTER_WATCHDOG_LOG`, существующие пути
  журнала, отметки очистки и `/tmp/router_watchdog.lock`.
- Сохранить расписание из конфигурации в локальном времени роутера, включая
  интервалы через полночь. Проверять актуальность конфигурации по изменению
  файла на минутных границах; атомарная замена JSON должна обнаруживаться.
- Здоровый текущий узел: свежая provider-owned проверка и выход без speedtest.
- Использовать только провайдеры из `use` целевой группы в Mihomo YAML и только
  допустимые конкретные члены production-группы. Сохранить исключения узлов.
- При отказе сначала включить первый свежепроверенный рабочий fallback,
  затем измерять кандидатов через отдельную группу `BENCHMARK`.
- Сохранить `top_n`, предел параллелизма healthcheck, таймауты, одну попытку
  обновления нужных провайдеров при неудаче и сохранение рабочего fallback.
- Среди успешно измеренных кандидатов в пределах минимальной задержки +50 мс
  выбирать максимальную скорость; равенства разрешать задержкой и именем.
- Поддержать `cloudflare` и внешний `/opt/bin/speedtest-go`, текущие размеры,
  потоки, раунды и ограничения времени. Внешний speedtest-процесс допускается:
  цель — убрать регулярный Python, а не менять способ измерения скорости.
- Сохранить очистку журнала по прошедшему времени, первый запуск без удаления,
  ручную очистку и общую блокировку всех изменяющих состояние операций.

## Планировщик и жизненный цикл

Планировщик — фоновая Tokio-задача в процессе панели. При запуске панели он
читает сохранённое состояние переключателя из настроек; значение по умолчанию —
включено, согласно предыдущему уточнению пользователя. Пользователь может
включать и выключать автоматическую работу на вкладке Watchdog. Режима
совместного исполнения и Python-fallback нет.
Он не требует открытого браузера и не создаёт Python-процесс для очередной проверки. Повторный запуск
панели не должен дублировать проверку одной и той же минутной отметки; пропущенные
отметки не проигрываются пачкой. Изменения часов не создают цикл частых запусков.

Сохранить общую межпроцессную `flock` между встроенным движком и ручными CLI-
операциями; при первой миграции учитывать ещё работающий старый процесс: неблокирующее получение, корректный статус busy/skip, без удаления
файла блокировки. Очередная отметка не запускает второй экземпляр незавершённой
проверки. Кеши панели не используются вместо свежих failover-healthcheck.

При остановке или перезапуске панели её встроенный watchdog тоже останавливается.
При завершении отменять принадлежащие операции задачи/загрузки и дочерний
speedtest, освобождать блокировку. При отсутствии/ошибке конфигурации сообщать
безопасную ошибку и ожидать следующего чтения; сервер панели остаётся доступным.

## Совместимость CLI, MCP и обновлений

Добавить нативный вход `xkeen-ui watchdog ...` для автоматической проверки,
чтения/частичного изменения настроек, ручного измерения, сравнения, явного выбора
узла и очистки журнала. Сохранить используемые MCP JSON-поля, stdin-патчи,
ограничение 64 КиБ, коды завершения, скрытие секретов и безопасные коды ошибок.

`--measure-selected` и `--find-faster --mcp-speed-profile` не меняют production-
выбор; профиль MCP остаётся 10 МБ × 4 потока × 1 раунд. Выбор через `--select-node`
повторно проверяет членство, доступность и `expected_current`. Не добавлять
автоматический выбор из результатов ручного сравнения. Сохранить поведение
существующего отдельного CLI `--find-faster --apply`, не расширяя права MCP.

Тонкий `/opt/bin/router-watchdog` всегда переадресует поддерживаемые операции
на `xkeen-ui watchdog ...`. Переключателя между движками и Python-fallback нет.
Это сохраняет фиксированный путь, используемый текущим MCP, без отдельного
процесса Python на роутере. Если нативный бинарник отсутствует или неисправен,
CLI возвращает ошибку и не запускает старую реализацию.

Нативный движок обновляется вместе с панелью. Старый Python-runtime не является
резервным исполнителем. Отдельный механизм обновления старого пакета не должен
переустанавливать Python-движок или сообщать об обновлении нативного движка:
связанные элементы интерфейса обновлений и уведомления должны отражать, что
watchdog теперь входит в панель. Остальные механизмы обновления панели сохраняются.

## Работа по умолчанию и миграция

При обычном запуске новой панели используется существующая конфигурация
watchdog и сохранённое состояние переключателя в настройках панели. При
отсутствии сохранённого значения встроенный watchdog включён по умолчанию.
Переключение доступно в интерфейсе; отдельные CLI-команды выбора движка,
маркер старого/нового режима, резервные копии для возврата старого движка
и процедура отката к самостоятельному watchdog не реализуются. Миграция
убирает старый Python-планировщик независимо от состояния переключателя:
выключенный встроенный watchdog не означает запуск старого.

Перед первой автоматической проверкой под общей блокировкой проверить
конфигурацию и доступность необходимых локальных файлов, убрать старые
автоматические задания watchdog из system/legacy crontab и отключить
ежеминутный `--sync-cron` hook. Сохранить все посторонние задания и исходный
JSON с настройками и секретом. Перезапускать cron только при изменении заданий.

Миграция должна быть идемпотентной при каждом запуске панели. Не запускать
новые проверки параллельно ещё работающему Python-watchdog. Если блокировка
занята или очистка прежнего планировщика не завершена, отложить запуск
нативных проверок, повторить подготовку и сообщить безопасную ошибку;
HTTP-сервер панели остаётся доступным. Не переключаться на старый движок.

Нативный `--sync-cron` очищает устаревшие задания watchdog вместо их
восстановления. Совместимый CLI-адаптер устанавливается вместе с новой
интеграцией. Повторная установка произвольного ранее выпущенного Python-пакета,
заменяющего адаптер и задания cron, не является поддерживаемой операцией.
Изменения упаковки ограничить интеграцией, не перестраивая систему публикации.

## Вкладка Watchdog в настройках панели

Точка входа — существующая шестерёнка в верхней панели, окно `SettingsModal`
(`frontend/src/components/modals/Settings.tsx`). Добавить отдельную вкладку
`Watchdog` рядом с существующими вкладками, используя текущие компоненты,
горизонтальную прокрутку вкладок и прокрутку содержимого.

Вверху вкладки — переключатель «Включить watchdog». Это включение/выключение
автоматических проверок встроенного Rust-движка, а не выбор между Rust и Python.
Состояние сохраняется на бэкенде в настройках панели, общее для всех браузеров
и сохраняется после перезапуска. По умолчанию включено; последнее уточнение
о вкладке не отменяет предыдущее требование о значении по умолчанию.

Выключение останавливает планирование и отменяет принадлежащую движку текущую
операцию/загрузки и дочерний speedtest с освобождением блокировки. Текущий
выбор production-узла сохраняется. Ручные действия через совместимый CLI/MCP
остаются доступны по явному запросу. Повторное включение запускает дальнейшую
работу по сохранённому расписанию без перезапуска панели и без одновременных
экземпляров. Очередные автоматические CLI-вызовы также учитывают выключение.

Все поддерживаемые параметры текущего watchdog доступны для редактирования:

| Раздел | Поля конфигурации | Представление |
| --- | --- | --- |
| Подключение к Mihomo | `controller`, `secret` | URL API, защищённое поле секрета |
| Группы | `target_group`, `benchmark_group`, `benchmark_proxy` | Production-группа, отдельная тестовая группа, HTTP(S) proxy для замеров |
| Проверки доступности | `top_n`, `healthcheck_parallelism`, `healthcheck_timeout_ms` | Число кандидатов 1–50, параллелизм 1–32, таймаут 250–10000 мс |
| Измерение скорости | `speed_test_provider`, `speed_connect_timeout_seconds`, `switch_wait_seconds` | Cloudflare/speedtest, таймаут соединения 1–30 с, неотрицательная конечная пауза переключения |
| Объём и параллелизм замеров | `download_bytes`, `parallel_streams`, `multi_rounds` | 1000000–200000000 байт на поток, 1–8 потоков, 1–4 раунда |
| Расписание | `schedule.windows[].start`, `end`, `every_minutes` | Редактирование всех окон: начало/конец HH:MM, интервал 1–1440 минут; добавление и удаление окон, включая переход через полночь |
| Журнал | `log_cleanup_days` | Интервал очистки 1–3650 дней |

Показывать русские подписи и единицы измерения. Ограничения и допустимые
значения соответствуют серверной валидации; устаревшие игнорируемые
`fresh_top_n`, `close_result_percent` и удалённый `speed_test_url` не возвращать.
Не изменять сохранённые настройки при открытии вкладки или её закрытии.
Параметры редактируются и сохраняются явной кнопкой «Сохранить»; переключатель
применяется отдельно и только после подтверждения сохранения сервером.
Несохранённый черновик не должен попадать в выполняющуюся проверку.

Секрет не возвращается в API в открытом виде и не подставляется в форму:
показывать только признак наличия. Пустое поле при сохранении означает
«оставить существующий секрет»; замена или удаление — явное действие.
Ошибки валидации показывать у полей. При ошибке сохранения не показывать
новые значения как успешно применённые. При отсутствующей конфигурации
показать необходимость настройки; фактические проверки не запускаются,
пока конфигурация невалидна, даже если сохранён переключатель «включено».

Загрузка и изменение параметров — авторизованные API панели, с общей
блокировкой конфигурации/операций и атомарной записью JSON. Запросы UI и MCP
используют одну конфигурацию и одни правила валидации. Смена настроек не
возвращает cron-планировщик; новое расписание подхватывает встроенный движок.

## Фоновый WebSocket и опрос

`useConnectionsSync` закрывает существующий WebSocket при `visibilityState !==
'visible'`, отменяет стартовый таймер и переподключение, устанавливает состояние
соединения в disconnected. При возвращении запускает одно подключение и
получает актуальный снимок. Не размножать обработчики, таймеры или соединения
при быстрых переключениях, размонтировании и Safari touch-восстановлении.
Последний снимок соединений можно сохранять до нового ответа.

Периодические GET `/api/control` и `/api/system` приостанавливаются в скрытой
вкладке; при возвращении выполняется одно немедленное обновление. В одной
вкладке не допускаются перекрывающиеся запросы одного вида.
Поток логов и поток прогресса обновления в этот пункт не входят.

## Общий кеш бэкенда

- Раздельные кеши `/api/control` и `/api/system` в общем `AppState`.
- Успешный ответ: TTL 2 секунды от завершения получения, по монотонным часам.
- Одновременные запросы одного вида объединяются в одно получение результата.
- Ошибку получения допускается разделять в течение 500 мс; не выдавать старую
  успешную статистику как свежую и не менять существующую форму ответа.
- Любая команда изменения состояния ядра сбрасывает кеш `/api/control`.
  Ответ GET, начатого до изменения, не может повторно заполнить кеш старым
  состоянием после сброса: нужна проверка поколения либо равнозначная защита.
- Для каждого вида хранится только один результат; фонового опроса без клиентов
  и общего кеша всех API не добавлять. Авторизация остаётся перед кешем.

## Проверка результата

1. Проверки паритета алгоритма на управляемом mock Mihomo: здоровый узел,
   немедленный fallback, отбор группы, 50/51 мс, ошибки и refresh, изоляция
   BENCHMARK, ручные операции без переключения и сменившийся baseline.
2. Проверки расписания, смены часов, изменения файла конфигурации, общей flock,
   конкуренции CLI/планировщика, завершения дочернего speedtest, очистки журнала.
3. Проверки запуска и миграции на временных файлах: чужие cron-задания
   сохраняются, повторный запуск безопасен, частичный сбой и занятая
   блокировка не создают двух планировщиков; CLI не возвращается к Python.
   Вкладка Watchdog: все поля доступны, сохранение/ошибки, маскировка секрета,
   сохранённое выключение после перезапуска, остановка текущего задания при
   выключении и повторное включение без дублирования проверок.
4. Проверки кеша: TTL, single-flight, ошибка, сброс после команды и гонка
   устаревшего GET со сбросом. Проверки WebSocket: hidden/visible/unmount,
   отмена таймеров и отсутствие дублирования.
5. Сборки frontend и Rust, существующие относящиеся к изменениям проверки,
   MIPSel cross-build с текущими параметрами статической musl-сборки.
6. Полный набор тестов router-watchdog требует отдельного разрешения по его
   AGENTS.md; не объединять такой запрос с правками и другими действиями.
7. На роутере: после согласования установки готовой сборки снять
   одинаковые CPU/RSS до/после, проверить отсутствие ежеминутного Python,
   поведение открытой/скрытой панели и сохранение работоспособности MCP.
   Реальные отказ/переключение узлов не вызывать без отдельного разрешения.

## Границы работ

Разработка в существующих каталогах, без worktree/копий проекта. Существующий
`benchmarks/` не изменять. Не менять подписки, маршрутизацию, список узлов,
расписание проверок, настройки speedtest и алгоритм выбора ради экономии CPU.
Установка новой панели означает автоматическую миграцию; встроенные проверки
учитывают сохранённое состояние переключателя в настройках, по умолчанию включено. Не ставить новую панель на роутер, не публиковать релиз и не отправлять
изменения в GitHub без отдельного согласования готового результата. Размер ожидаемого снижения общей загрузки CPU пока не обещается.

Структуру модулей, минимальные новые зависимости и конкретные команды проверок
определяет план реализации в пределах этих требований.
