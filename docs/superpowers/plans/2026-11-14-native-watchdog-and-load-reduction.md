# План реализации встроенного watchdog и снижения нагрузки

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Track progress below; no worktrees or project copies.

**Цель:** выполнить согласованный перенос watchdog в Rust, добавить управление в настройках, приостановку скрытого WebSocket и общий кеш API.

**Архитектура:** алгоритм watchdog и его конфигурация отделены от планировщика/CLI/API. Последние используют один движок и общую flock. Существующая авторизация закрывает новые API. Независимые части: движок, кеш, frontend; интеграцию и миграцию выполняет ведущий агент.

**Стек:** Rust, Tokio, Axum, reqwest, yaml-rust2; React/TypeScript, существующие UI-компоненты. Без Go, Angular и новых сервисов.

**Спецификация:** `docs/superpowers/specs/2026-11-14-native-watchdog-and-load-reduction-design.md`, согласована пользователем 14 ноября 2026 года после уточнения вкладки настроек.

## Общие ограничения

- Работать в текущем каталоге на `feature/native-watchdog`; не менять `benchmarks/`.
- Не разворачивать новую версию, не менять живой cron/узлы, не публиковать и не отправлять изменения без отдельного согласования готового результата.
- Все поддерживаемые параметры, MCP-форматы, таймауты, профиль 10 МБ × 4 × 1, алгоритм и +50 мс сохраняются.
- Встроенный движок включён по умолчанию; состояние переключателя сохраняется в `watchdog.enabled` в конфигурации панели. Python-fallback и откат не реализуются.
- Не возвращать существующий секрет в UI/API; пустое поле UI сохраняет секрет, очистка явная.
- Не запускать полную Python-серию router-watchdog без отдельного разрешения его AGENTS.md. Новые Rust-проверки с mock API и временными файлами входят в реализацию.
- Ручные изменения и автоматический цикл используют один `/tmp/router_watchdog.lock`.

## Интерфейсы между частями

- `watchdog_engine::config::Config`: публичные поля текущей JSON-схемы, Clone/Serialize/Deserialize, `validate(&self) -> Result<(), String>`, `public_view(&self) -> Value`.
- `config::load(path: &Path) -> Result<Config, String>`; `config::validate_patch(current: &Value, patch: &Value) -> Result<Value, String>` сохраняет неизвестные существующие поля, запрещает неизвестные новые поля.
- `automatic(cfg: &Config, mihomo_path: &Path, log_path: &Path) -> Result<(), String>` — async.
- `measure(cfg: &Config, mihomo_path: &Path, log_path: &Path, find_faster: bool, mcp_profile: bool, apply: bool) -> Result<Value, String>` — async.
- `select(cfg: &Config, mihomo_path: &Path, log_path: &Path, node: &str, expected_current: &str) -> Result<Value, String>` — async.
- Все ошибки движка безопасны и не содержат URL подписок/секретов. Внутренние журналы не пишутся в stdout MCP.
- `watchdog_engine::runtime` принадлежит ведущему агенту: Paths, Runtime, общее управление задачей, миграция, сохранение enabled, API и CLI. Глобальный Runtime используется обработчиками; тесты создают отдельные экземпляры с временными Paths.
- Авторизованный GET `/api/watchdog/config` → `{success, enabled, config, editable_fields, secret_configured}`. `config` не содержит `secret`.
- Авторизованный PATCH `/api/watchdog/config` принимает `{enabled?: boolean, config?: object}`. Успех — `{success:true}`; безопасная ошибка — `{success:false,error:string}`. Отсутствующий секрет не меняется; `secret:""` явно удаляет его. Частичный config-патч использует общую серверную валидацию.
- Дополнительного поля в frontend AppSettings для watchdog не требуется: вкладка получает отдельный API.
- `AppState` получает два кеша; ведущий агент добавляет их инициализацию в main. Агент кеша не правит main и Cargo.toml.

## Приоритеты проверки

1. Параллельный CLI/планировщик и отмена speedtest при выключении; flock удерживается до прекращения операции.
2. Ошибка миграции не оставляет двух активных планировщиков; чужие cron-задания сохраняются.
3. Секрет не очищается случайно и не возвращается в HTTP-ответах/логах.
4. Сброс кеша при команде управления защищён от позднего завершения старого GET.
5. Hidden/visible/unmount не создают лишних сокетов, таймеров и перекрывающихся запросов.

## Журнал решений

- Реализация уже разрешена согласованием проекта; повторно не запрашивать разрешение на каждый этап. Выбранная организация — независимые bounded implementers и отдельный обзор, без новых worktree.
- Состояние enabled хранится в JSON настроек панели; отдельный API не меняет существующий frontend AppSettings.
- Модули frontend, кеша и движка независимы; общие изменения main/Cargo и runtime принадлежат ведущему агенту.
- Локальные git-коммиты не обязательны для проверки готового изменения; не включать старые неотслеживаемые benchmarks в изменения задачи.
